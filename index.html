Career-First Engineering Campaigns

The objective is not to finish the internet. The objective is to become materially harder to reject for a better-paying software engineering role while building deep foundations that compound.

ONE primary campaign at a time. Job search + interview practice stay active in parallel. Everything else is a library, not a debt.
20–24hweekly outside-work target
8–12focused weeks per campaign
1main technical campaign
Nowstart applying — never “after ready”
Always on LAND THE BETTER JOB

This outranks everything.

Do not spend six months “preparing” before applying. Your current experience is already marketable. The learning plan exists to increase hit rate while applications are already moving.

Weekly allocation

  • 8–10h: DSA / coding interviews
  • 4–5h: applications, referrals, recruiter calls, behavioral prep
  • 2h: system-design / production stories
  • 8–10h: current technical campaign

DSA rule

3–4 Blind 75 problems/day is fine temporarily, but optimize for recall + pattern recognition, not raw count. A problem is not “done” until you can re-solve it cold.

Every week
Pipeline 8–12 high-quality applications. 5 targeted referral/outreach messages. Track every role and follow-up.
Deliverable: active interview pipeline, not a prettier study plan.
Every week
Coding 5 timed sessions. Re-solve misses after 2–3 days. Maintain a one-page pattern sheet: two pointers, sliding window, stack, BFS/DFS, heap, intervals, binary search, backtracking, DP.
Every week
Interview narrative Practice 2 stories from your real work: production bug, ownership, disagreement, performance improvement, ambiguous project, failure. Say exactly what you did.
Every 2 weeks
Mock loop One coding mock + one 30–45 min system-design/backend discussion. Record where your explanation breaks.

Exit criteria

Campaign 01 · next SYSTEMS + NETWORKING: MAKE THE WEB PHYSICAL

10 weeks. One question.

What actually happens from run program to process → file descriptor → socket → HTTP request → server response?

This is where your current reading list belongs. Do not read every source cover-to-cover. Use each source for a specific layer.

Primary build

Finish the CodeCrafters HTTP Server. Then rebuild the core yourself in a small repo without the scaffold.

Commit rule

Frequent commits are good, but 10–20 commits/day is not the objective. Commit at coherent learning checkpoints. A clean history of 3 meaningful commits beats 17 “progress” commits.

Week 1
Processes: stop treating programs as magic. OSTEP ch. 5 Process API. CS:APP ch. 1 selectively. Write tiny fork/exec/wait experiments.
Explain process vs program, parent/child, exec, exit status without notes.
Week 2
Unix I/O model. TLPI ch. 4–6 selectively. Kernighan & Pike ch. 2–3. Open/read/write/close; stdin/stdout/stderr; redirection.
Implement file copy + redirection experiments using low-level APIs.
Week 3
Pipes, processes, shell intuition. Build a minimal shell: command execution, >, one pipe, exit status.
A shell you can explain syscall-by-syscall.
Week 4
TTY / PTY / job-control questions. TLPI 24–27 selectively → ch. 34 → ch. 62. Do not memorize terminal trivia; trace an interactive shell session.
Draw: keyboard → terminal emulator → PTY → shell → child process.
Week 5
Networking model. Top-Down 1.5, 2.1.2, 2.1.3, 2.1.5. Focus on processes communicating, transport service, encapsulation.
Explain what changes at each layer when an HTTP request leaves your laptop.
Week 6
HTTP as bytes, not a library call. Top-Down 2.2.1 + 2.2.3. Use curl -v, netcat, browser devtools. Manually send an HTTP request.
Parse a raw request and produce a raw HTTP response by hand.
Week 7
Sockets. Top-Down 2.6.2 + CS:APP ch. 11 selectively. Finish the socket/listener/request portions of CodeCrafters.
TCP echo server + HTTP server; explain bind/listen/accept/read/write.
Week 8
Concurrency. Skim CS:APP ch. 12. Compare sequential, thread-per-connection, and async models. Connect to your asyncio reading.
Benchmark two concurrency approaches under multiple clients.
Week 9
Rebuild without the rails. New empty repository. Rebuild a small HTTP/1.1 server without looking at the CodeCrafters implementation first.
Routes, headers, body, files, concurrent clients, logs.
Week 10
Instrument + ship. Use strace/lsof, benchmark, document architecture, draw packet/process diagrams, write a serious README.
A public project that demonstrates systems understanding, not just completion badges.
Campaign 02 BACKEND DEPTH: PYTHON + DJANGO + POSTGRES

Highest direct career ROI.

Turn your existing professional stack into an unfair advantage. You do not need twelve frameworks. You need to sound and operate like someone who has looked underneath the one they use every day.

Resources

  • Fluent Python — selected data model / iterator / generator / concurrency sections
  • Django source for request lifecycle, QuerySet, middleware
  • PostgreSQL docs + EXPLAIN ANALYZE
  • Your real work codebase whenever a concept maps directly
Weeks 1–2
Python runtime model. Data model, mutability, iterators/generators, descriptors, closures, import behavior. Inspect with dis.
Weeks 3–4
Django request lifecycle. URL resolution → middleware → view/DRF → ORM → response. Read actual source at each hop.
Weeks 5–6
SQL performance. Indexes, joins, N+1, select_related/prefetch_related, EXPLAIN ANALYZE, transactions and locks.
Weeks 7–8
Background work + caching. Celery/Redis mental model, retries, idempotency, cache invalidation, failure modes.
Week 9
Debugging/profiling. pdb, logging, correlation IDs, py-spy/cProfile, git bisect. Reproduce bugs deliberately.
Week 10
Capstone. Build/upgrade one backend service and publish architecture, load-test numbers, bottlenecks found, and tradeoffs.
Campaign 03 DATABASES + DISTRIBUTED SYSTEMS

After OS/networking.

Now replication, consistency, logs, caches, queues and failure modes will attach to machinery you already understand.

Primary: selected DDIA chapters + hands-on Postgres/Redis experiments. One CodeCrafters Redis track is an excellent fit here.

Weeks 1–2
Storage/indexes. B-trees, logs, pages, cache behavior.
Weeks 3–4
Transactions. Isolation, locks, MVCC, deadlocks. Reproduce anomalies locally.
Weeks 5–6
Replication/partitioning. Failure cases before terminology.
Weeks 7–9
Build. CodeCrafters Redis or a tiny persistent KV store with protocol, TTL, persistence, concurrency.
Week 10
Design. Defend tradeoffs for a scalable service using cache, queue, DB, retries, idempotency.

Operating rules HOW NOT TO RUIN THE PLAN
  • Never run two deep campaigns at once.
  • Applications begin now. No “I’ll apply once I finish OS/networking.”
  • Projects beat resource completion. Stop reading when you have enough to build the next thing.
  • AI may explain, critique, test, or review. During deliberate-practice builds, you write the core mechanism yourself.
  • Rebuild from memory. Every campaign contains at least one blank-folder rebuild.
  • Measure. Benchmark, profile, test, inspect syscalls/queries/packets. Convert claims into observations.
  • Ship. README, diagrams, benchmarks, lessons, and a runnable artifact.
  • Stop at the campaign boundary. Unfinished chapters can remain unfinished.
